# 需求文档：操作日志升级（Request / Response 可查）

## 1. 背景与目标

系统已通过 `@OperationLog` 切面将关键写操作落库到 `sys_operation_log`，前端「操作日志」页支持按模块 / 结果 / 时间分页查询。

**现状不足**

- 仅保存方法入参的字符串摘要（`params`），无法还原完整 HTTP 请求上下文
- **不记录响应体**，审计时无法核对接口返回内容
- 列表页无详情入口，长文本无法阅读

**目标**

- 每条操作日志可查看 **Request 信息** 与 **Response 信息**
- 敏感字段脱敏，体积可控，不影响接口性能
- 兼容已有日志数据；历史记录无 response 时友好展示

## 2. 角色与权限

| 动作 | SUPER_ADMIN | HR_ADMIN | 其他角色 |
|------|:-----------:|:--------:|:--------:|
| 分页查询操作日志 | ✓ | ✓ | ✗ |
| 查看单条 Request / Response 详情 | ✓ | ✓ | ✗ |

权限沿用现有：`page:/hr/operation-log` + 接口 `hasAnyRole('SUPER_ADMIN','HR_ADMIN')`，本期不新增独立权限码。

## 3. 与现有能力的关系

| 维度 | 现有 | 升级后 |
|------|------|--------|
| 落库触发 | `@OperationLog` 注解方法 | 不变 |
| 请求内容 | `params`：Controller 方法参数 `toString` | 结构化 Request（见 §4.1），`params` 可保留兼容或合并 |
| 响应内容 | 无 | 成功：响应体摘要；失败：错误信息（可与 `error_msg` 并存） |
| 前端 | 仅列表 | 列表 + **详情抽屉/弹窗** 展示 Request / Response |

## 4. 功能需求

### 4.1 Request 信息（需落库并可查）

至少包含：

| 字段含义 | 说明 |
|----------|------|
| HTTP 方法 + URI | 与现有 `method` 一致或拆分展示 |
| Query 参数 | URL query string（无则空） |
| Request Body | JSON / 表单类入参；文件上传仅记文件名与大小，不存文件二进制 |
| 客户端 IP | 现有 `ip` |
| Content-Type | 可选，便于区分 json / multipart |

**脱敏（必须）**

- 密码、确认密码、旧密码、新密码 → `***`
- MFA / 验证码 / token / Authorization → `***`
- 人脸特征、base64 大图等超大字段 → 占位说明（如 `[omitted:face]`）

### 4.2 Response 信息（需落库并可查）

| 场景 | 记录内容 |
|------|----------|
| 业务成功 | 接口返回对象序列化后的 JSON（通常为 `Result` 包装） |
| 业务/系统异常 | 异常类名 + message；可与现有 `error_msg` 对齐 |
| 文件下载 / 流式响应 | 不落完整流，记占位：`[binary/stream omitted]` |
| 超长内容 | 截断并标注 `...(truncated, total=N)` |

### 4.3 前端交互

1. **列表**：保持现有列（时间、操作人、模块、操作、请求、结果、耗时、IP）；增加「详情」操作列
2. **详情**：抽屉或弹窗（宽度适中，约 640～720px）
   - 基本信息：时间、操作人、模块、操作、IP、结果、耗时
   - **Request**：JSON / 文本只读展示，支持一键复制
   - **Response**：同上
   - 失败时高亮错误信息
3. 列表接口 **可不返回** 完整 request/response 大字段，避免拖慢分页；详情走按 id 查询（一期推荐 **详情单独接口**）

### 4.4 非功能

- 单字段落库上限建议：Request / Response 各 **不超过 8KB～16KB**（截断）
- 日志写入失败 **不得影响** 原业务接口成功/失败结果
- 写入尽量轻量（同步截断后 insert 可接受；若耗时可观测再改为异步）
- 历史数据：`response` 为空时详情展示「无响应记录（升级前日志）」

## 5. 非目标（本期不做）

- 不记录全部无 `@OperationLog` 的只读接口
- 不做日志全文检索（Elasticsearch 等）
- 不做日志导出 Excel（可后续迭代）
- 不改动登录接口强制打操作日志（登录仍可不记 body，或保持脱敏省略）

## 6. 验收标准

| ID | 验收标准 |
|----|----------|
| AC-001 | 带 `@OperationLog` 的写操作成功后，详情中可看到 Request（含 body/query）与 Response JSON |
| AC-002 | 带注解的操作失败时，详情可看到 Request，以及失败 Response/错误信息 |
| AC-003 | 密码、token、MFA 等敏感字段在 Request 中已脱敏 |
| AC-004 | 超长 Request/Response 被截断且不影响业务接口正常返回 |
| AC-005 | 列表分页性能与现网接近；完整报文仅在详情接口返回 |
| AC-006 | HR_ADMIN / SUPER_ADMIN 可查详情；其他角色无法访问接口 |
| AC-007 | 升级前历史日志仍可列表查询；详情对缺失字段友好提示 |
| AC-008 | 文件上传类操作不落库文件二进制，仅文件名等信息 |

## 7. 开放问题（实现前确认）

1. Request 是否需要记录 **部分请求头**（如 `User-Agent`、`Content-Type`）？建议一期只记 Content-Type。
2. Response 截断上限：建议 **8192 字符/字段**，是否同意？
3. 详情 UI：偏好 **抽屉（Drawer）** 还是 **弹窗（Modal）**？建议 Drawer。
